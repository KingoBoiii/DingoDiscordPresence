## Decisions

### D1. `EndUnix` is appended to `Activity` and is sent only when it is after the start

```cpp
// include/DingoDiscordPresence/DiscordPresence.h, Activity, after Buttons
// Unix seconds; Discord counts down to it. Left off when it is not after StartUnix.
int64_t EndUnix = 0;
ActivityType Type = ActivityType::Playing;   // D2
```

`ActivityJson` (`src/Json.h:194-197`) writes one `timestamps` object holding `start`, `end` or both:

```cpp
const bool start = activity.StartUnix > 0;
const bool end = activity.EndUnix > 0 && (!start || activity.EndUnix > activity.StartUnix);
// "timestamps":{"start":S}, {"end":E} or {"start":S,"end":E}
```

- **Appended, not next to `StartUnix`.** That way neither positional nor designated aggregate init in a game
  breaks (`DiscordPresence.h:30-32`).
- **Dropping an end that isn't after the start is a precaution.** Discord may reject the whole activity for it,
  which would take the card down; that is unconfirmed. Dropping only the end keeps the rest of the card up.
- **An end already in the past is sent as it is.** Whether that makes sense is the game's call.
- **A changed end resends.** `operator==` stays defaulted, so `SetActivity` (`src/Client.cpp:112-121`) sees the
  change.

### D2. `ActivityType` lists only the four types Discord accepts over the pipe

```cpp
enum class ActivityType
{
	Playing = 0,
	Listening = 2,
	Watching = 3,
	Competing = 5
};
```

- **The values are Discord's own numbers.** Streaming (1) needs a Twitch or YouTube URL, and Custom (4) is
  refused over RPC.
- **`Playing` writes no `type` key,** so a v0.1 game's frame is byte-identical. Any other type writes `"type":N`
  straight after `details` (`src/Json.h:189`).
- **The key goes through a `switch` with a `default:` that writes nothing.** Never `static_cast<int>(t) != 0`:
  that would send 1 and 4. A partial enum switch without a `default:` also fails `-Wswitch -Werror`.

### D3. `ConnectionStatus`: a live poll and one callback, with no user data

```cpp
enum class ConnectionStatus
{
	Disabled,   // Config::Enabled false, or SetEnabled(false)
	DryRun,     // empty AppId: nothing is ever opened. Wins over Disabled
	Waiting,    // enabled, no READY yet: Discord not running, connecting, or between retries
	Connected   // the pipe is open and READY came: IsConnected() is true
};
using StatusFn = void(*)(ConnectionStatus status, void* user);

// Config
StatusFn OnStatus = nullptr;
void* StatusUser = nullptr;

// Client
ConnectionStatus GetStatus() const;
```

**Why it exists, and its name**
- **It tells "off" from "not running".** `IsConnected()` (`src/Client.cpp:193-196`) can't tell "off in settings"
  from "Discord isn't running", and a settings row needs exactly that.
- **Not called `Status`.** `<X11/Xlib.h>` has `#define Status int`, the Linux twin of the `<Windows.h>` rule. The
  enumerators avoid the X11 and Windows macros too (`None`, `Success`, `True`, `False`, `Bool`, `ERROR`).

**What `GetStatus` returns**
- **It is live:** computed from `m_DryRun`, then `m_Enabled`, then `IsConnected()`. It allocates nothing.
- **DryRun wins over Disabled.** Nothing is ever opened either way, and a dry-run toggle stays quiet.

**When `OnStatus` fires**
- **Only on a change.** `Impl::ReportStatus()` compares against `std::optional<ConnectionStatus> m_LastStatus`.
  It starts empty, so the first value is always reported.
- **From `Client::Update`, `Client::SetEnabled` and `Client::Clear`,** in the `Client` wrappers after the `Impl`
  call (`src/Client.cpp:486-504`). Not at the end of `Impl::Update`, which has early returns at `:66-69`, `:78`,
  `:85`, `:90` and `:95-98`.
- **`Clear` is in the list because it can disconnect.** `Clear` calls `ClearCard`, then `SendClear`, and a failed
  write ends in `Disconnect` (`:124-150`, `:223-234`). `SetActivity` never writes, so it needs no report.
- **Never from `Shutdown` or `~Client`.** Calling into a game while it destroys the client is a use-after-free
  waiting to happen. `Shutdown` (`:172-181`) is shared with `SetEnabled(false)`, so `SetEnabled` reports after it
  returns.
- **The first report is the first `Update`, `SetEnabled` or `Clear` call,** whichever comes first. A game that
  calls `SetEnabled(false)` from its settings load before any `Update` gets Disabled at that moment.

**What the callback may do**
- **No re-entrancy loop.** `ReportStatus` stores `m_LastStatus`, sets `m_Reporting`, calls the game, and clears
  `m_Reporting`. An inner `ReportStatus` (the callback calling `SetEnabled` or `Clear`) returns at once. Whatever
  the callback changed is reported by the next `Update`, `SetEnabled` or `Clear`. There is no loop, so a callback
  that toggles every time still terminates: one toggle per frame.
- **It may call `SetActivity`, `Clear`, `SetEnabled` and `GetStatus`.** It must not call `Update` and must not
  destroy the `Client`. The header comment says so.
- **Nothing after the call.** `ReportStatus` touches nothing but `m_Reporting` after calling the game.

**What it passes**
- **No user data, ever.** No user id, name or avatar is passed: READY's body stays private (`CLAUDE.md`,
  Privacy).
- **The same shape as `LogFn`:** a function pointer plus `void* user`. No `std::function` in the header and no
  allocation.
- **One accepted edge:** a READY followed by a failed write in the same `Update` goes Waiting to Waiting, and
  never reports Connected.

## API and ABI

- **Header:** `ActivityType`, `Activity::EndUnix`, `Activity::Type`, `ConnectionStatus`, `StatusFn`,
  `Config::OnStatus`, `Config::StatusUser`, `Client::GetStatus`. All are additions, and the new fields sit at the
  end of their structs.
- **ABI:** `Activity` and `Config` change size, so the release is binary-incompatible. A game's source still
  compiles unchanged, because every new field is appended.
- **Headstone and 200 OK:** each bumps its `vendor/DingoDiscordPresence` package to v0.2.0 and rebuilds. No code
  has to change. Using the new parts is the games' choice, in their own repos: a countdown, `Competing` for ranked
  play, a status line in a settings row.

## Testing

**Phase 1, unit (`tests/JsonTests.cpp`):**
- `timestamps` is written correctly for each case:
  - an end with no start writes `{"end":E}`;
  - a start and an end write both, start first;
  - an end equal to the start, or before it, writes the start only;
  - a negative start with a positive end writes the end only.
- Each of the four types. Playing writes no `type` key, and `Json_ActivityWithOnlyDetails` stays byte-identical.
- `static_cast<ActivityType>(1)`, `(4)` and `(99)` write no key.

**Phase 1, fake (`tests/ClientFakeTests.cpp`):**
- An activity with an end and `Competing` arrives with both keys.
- Changing only `EndUnix` resends after the gap.

**Phase 2, fake** (a recorder with a `std::vector<ConnectionStatus>` behind `StatusUser`):
- **Connecting:**
  - A fresh client reports Waiting on its first `Update`, then Connected after READY.
  - A dropped handshake (`src/Client.cpp:271-275`) stays Waiting and never reports Connected.
- **Losing the link** reports Waiting in each of these cases:
  - CLOSE from the fake, and then a reconnect reports Connected again;
  - the fake dropping the connection;
  - an oversize frame (the pattern of `:238`);
  - the write timeout (the pattern of `:441-472`).
- **Enabling and disabling:**
  - `SetEnabled(false)` while Connected reports Disabled. `SetEnabled(true)` then reports Waiting, then Connected.
  - `SetEnabled(false)` while Waiting reports Disabled.
  - `SetEnabled` with the current value reports nothing.
  - `Enabled = false` at start reports Disabled on the first `Update`.
  - `SetEnabled(false)` before any `Update` reports Disabled at once.
- **Dry run:**
  - It reports DryRun once.
  - An empty AppId with `Enabled = false` reports DryRun, and `SetEnabled` toggles report nothing.
- **Re-entrancy:**
  - `SetActivity` from inside `OnStatus(Connected)` gets its activity sent.
  - `Clear` from inside `OnStatus(Connected)` sends the null activity.
  - `SetEnabled(false)` from inside `OnStatus(Connected)` makes no nested call. The next `Update` reports Disabled.
  - A callback that toggles `SetEnabled` on every call terminates, with one report per `Update`.
- **Wiring:**
  - There is one call per change: ten `Update`s while connected add none.
  - `StatusUser` is passed through.
  - `OnStatus == nullptr` is allowed, and `GetStatus` still works.
  - Destroying a connected client makes no call.
- **Privacy:** the SECRET-USER test (`Fake_LogFramesLogsFramesButNothingOfWhatDiscordSent`) still passes.

## Risks

- **Discord ignores `type` over RPC.** It was ignored for years, and is reported to work since about 2024 for 0,
  2, 3 and 5. The live test is the proof. If Discord ignores it, the card shows "Playing" and nothing breaks.
- **An end alone may not show a countdown** for Playing on every Discord client, only a bar for Listening or
  Watching. It's harmless, and the live test says which.
- **A game mixes an old header with a new lib.** The packages always ship them together, and the changelog states
  the ABI break.
